# LGHS Fleet Web UI — Second Research Pass (2026-08-31)

This document records the second design/engineering research pass used before the first controller-hosted UI test.

## Product principles reinforced by research

1. The default page must answer an operational question, not display everything the system can measure.
2. Fleet-wide scanning should use dense, comparable tables; charts belong in drill-downs where time and correlation matter.
3. Status color is supplemental. Labels, icons, text, thresholds, and ordering must carry the meaning too.
4. Navigation must have durable homes for future functionality instead of accumulating miscellaneous menus.
5. Motion is a feedback/identity layer, never the information architecture.
6. Production must never fabricate telemetry. Missing history is shown as unavailable until an authoritative history endpoint exists.
7. Current state and historical telemetry have different data lifecycles and should be modeled separately.
8. Cloudflare Access authenticates the browser, but LGHS still validates the signed Access JWT and applies its own role authorization at the origin.

## Cloudflare UI lessons worth adopting without copying

Cloudflare's dashboard redesign work repeatedly emphasizes scalable information architecture, responsive behavior, consistent component language, restrained visual styling, and small pieces of brand illustration rather than decorating every surface. Their accessibility work also shows that analytics must not rely on color alone and that chart data should have textual/tabular alternatives.

LGHS translation:

- compact left navigation with clear product areas;
- quiet surfaces and borders, with saturated color reserved for real state;
- a small amount of recognizable brand art in identity/onboarding surfaces;
- strong light/dark themes;
- data-first pages with progressive disclosure;
- downloadable or tabular alternatives for historical charts once history is live.

## Visual identity direction: Signal Field

The first LGHS-specific visual motif is **Signal Field**: a pixel/raster network field made from low-contrast points, links, rings, and moving signal packets. It represents a classroom fleet communicating through a controller without copying Cloudflare's globe.

Rules:

- decorative only (`aria-hidden`);
- never behind dense tables or critical controls;
- used on the sign-in/session boundary, empty states, and a restrained overview masthead;
- low contrast so operational content wins;
- no flashing;
- animation automatically stops for `prefers-reduced-motion` and when the document is hidden;
- requestAnimationFrame, with a 30 fps cap for the decorative canvas;
- high-DPI canvas scaling is bounded to avoid oversized iOS canvases;
- no animation libraries or WebGL are required for the background motif.

## Motion system

- Micro interaction: 90–140 ms.
- Navigation/panel state: 140–200 ms.
- Dialog/drawer: 180–240 ms.
- No spring/bounce motion for operational actions.
- Animate compositor-friendly transform/opacity where possible.
- Loading indicators communicate waiting; they do not continuously animate healthy status.
- Status changes may briefly emphasize the affected row, but do not reorder while the user is actively interacting with a table.

## Dashboard hierarchy

### Overview

Questions:
- Is the fleet healthy?
- What needs action now?
- Is a rollout underway?
- Are there resource outliers?

No generic time-series wall here.

### Fleet

Primary operations surface. Search, filter, sort, compare, multi-select, then drill down. Client-side processing is fine for the current school fleet; if the fleet grows substantially the API moves filtering/sorting/pagination server-side. Virtualization is only added when real row counts justify it.

### Device

Current state first, then historical telemetry. Health checks are authoritative records from the agent/controller, not re-derived in the browser once the structured health endpoint is connected.

### Alerts

Actionable state. Severity + reason + observed/expected + age + acknowledgment + remediation.

### Deployments

Wave/phase progress, target immutable commit, affected scope, health gate, failures, retries, rollback and audit trail.

### Sudo

Pending approvals get an explicit exact-command review surface. No bulk approval.

### Activity

Single chronological operational/audit stream with filters. It is the place to understand what changed, by whom, and why.

### Provisioning (future navigation group)

Enrollment state, first boot, Bluetooth exchange, Wi-Fi, Fleet identity, tunnel issuance, SSH key finalization, failure stage, retry/recovery. This will be added when the first hardware protocol is stable.

## Data architecture decisions

### Current state

Keep the 5-second agent report cadence for controller freshness and command delivery. The browser should receive a normalized current snapshot and can refresh every 5 seconds initially; SSE will later push invalidation/state events rather than continuously streaming every metric sample.

### History

Do not render synthesized history. Add an authoritative history store with bounded retention and server-side downsampling. Planned first tier:

- raw/30-second sample: 24 hours;
- 5-minute rollup: 90 days;
- optional 1-hour rollup: 1 year.

Network rates are calculated from monotonic interface byte counters and reset on boot-id change or counter regression.

## Authentication and authorization

- Cloudflare Access is the primary login experience at `fleet.scenicrouteservers.com`.
- The origin validates `Cf-Access-Jwt-Assertion` signature, issuer, audience and expiry.
- LGHS role file maps verified identities to owner/operator/viewer.
- Unknown identity: deny.
- Browser never receives Fleet admin token, Cloudflare account API token, or device tunnel token.
- Every state-changing route requires origin check, CSRF/custom-header defense, role authorization, validation, audit event and an idempotency strategy where applicable.
- Dangerous operations require confirmation that states target/scope/impact in plain language.

## Bluetooth finding from full-system review

The existing application protocol is sound in concept: per-device Fleet token authentication, ephemeral X25519, HKDF, AES-GCM, transcript binding and no plaintext Wi-Fi/tunnel credential transfer.

However, the current student `lghs-bt-bootstrap.service` uses `ProtectSystem=strict` while `lghs-cloudflare-install` needs to create `/etc/cloudflared/token`, `/etc/systemd/system/lghs-cloudflared.service`, and potentially `/usr/local/bin/cloudflared`. That sandbox blocks the current zero-touch Cloudflare install path. This must be fixed before the fresh-image Bluetooth acceptance test.

For tomorrow, keep the tested RFCOMM application transport and fix lifecycle/sandbox reliability. Longer term, migrate the same authenticated/encrypted application protocol onto a BlueZ D-Bus GATT service with LE advertising. BlueZ provides `GattManager1` and `LEAdvertisingManager1` specifically for locally published GATT services/advertisements and gives a cleaner discovery path than the compatibility SDP/RFCOMM layer.
