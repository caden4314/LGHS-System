# LGHS 0.6 RC Hardware Validation

This is the release gate for LGHS 0.6 after source freeze. A release candidate is not promoted to `0.6.0` until every required case below passes on real hardware or is explicitly waived with a documented reason.

## Test topology

Minimum:
- 1 controller Pi (`LGCSCONT`)
- 2 student Pis for rollout testing
- 1 additional student Pi preferred for offline/power-loss cases
- controller and students enrolled through the same paths used by the production image

Record for every run:
- RC version
- exact Git commit
- controller hostname/boot ID
- student device IDs/boot IDs
- start/end time
- result and failure notes

## A. Fresh install / image acceptance

- [ ] Controller fresh install completes without manual repair.
- [ ] Student fresh install completes without manual repair.
- [ ] Required services are enabled and active after reboot.
- [ ] Fleet API starts and retains SQLite state across reboot.
- [ ] Fleet Control opens and lists enrolled devices.
- [ ] Student reports hostname, model, RAM, serial, version, exact current commit, boot ID, health, and last seen.
- [ ] Bluetooth bootstrap provisions a fresh student when enabled.
- [ ] Bluetooth bootstrap stops permanently after successful HTTPS/Fleet API provisioning.
- [ ] No Wi-Fi credential is exposed through student-visible files or UI.

## B. Exact-commit update acceptance

- [ ] Single student exact-SHA deployment succeeds.
- [ ] Moving branch name and short SHA are rejected.
- [ ] `SUCCEEDED` command alone does not mark device in-sync.
- [ ] Device becomes `in_sync` only after reporting the exact target SHA.
- [ ] Previous commit is recorded for rollback.
- [ ] Same action with a different target SHA creates distinct controller work.
- [ ] Duplicate delivery of the same controller command does not execute local work twice.

## C. Idempotency / restart safety

- [ ] Lose the acceptance reply after local enqueue; redelivery does not enqueue the update twice.
- [ ] Restart `lghs-agent` while command is `received`; command is recovered safely.
- [ ] Restart `lghs-command-executor` after local enqueue; redelivery is idempotent.
- [ ] Restart controller while command is queued/delivered; state resumes without duplicate execution.
- [ ] Simulated uncertain local execution is held and requires explicit retry.
- [ ] Idempotency-key reuse with a different payload is rejected.
- [ ] Duplicate reboot delivery does not arm a second reboot transaction.

## D. Canary / phased rollout

- [ ] Frozen group membership does not change after deployment creation.
- [ ] Canary device is dispatched first.
- [ ] Healthy canary completes required soak before next wave.
- [ ] Health regression during soak resets the soak timer.
- [ ] Canary failure pauses immediately.
- [ ] A failed canary cannot auto-continue.
- [ ] Later-wave failure threshold pauses at configured threshold.
- [ ] Below-threshold failure does not deadlock later waves.
- [ ] Controller restart during soak preserves rollout timing/state.

## E. Structured health gates

Force each required failure individually and verify rollout blocks with a specific reason/remediation:
- [ ] stale telemetry
- [ ] NetworkManager inactive
- [ ] LGHS policy inactive
- [ ] LGHS agent inactive/recovery condition
- [ ] command executor unhealthy
- [ ] root filesystem read-only
- [ ] insufficient disk space
- [ ] clock not synchronized
- [ ] current undervoltage
- [ ] current throttling
- [ ] reboot required
- [ ] controller connectivity stale

Also verify:
- [ ] historical undervoltage/throttle remains advisory and does not permanently block rollout.
- [ ] clearing a required failure returns the gate to healthy and restarts soak as expected.

## F. Recovery controls

- [ ] Retry Failed creates a new command ID and increments attempt.
- [ ] Resume refuses while the original pause condition remains active.
- [ ] Cancel Remaining cancels undispatched/guaranteed-cancelable work only.
- [ ] Accepted/running work is not falsely reported canceled.
- [ ] Rollback creates a new deployment rather than rewriting history.
- [ ] Rollback targets each device's recorded previous exact SHA.
- [ ] Mixed previous SHAs create safe separate rollback deployments.
- [ ] Unsafe rollback is skipped when current commit no longer matches the deployment target.

## G. Maintenance / reboot

- [ ] Device maintenance policy overrides group policy.
- [ ] Multiple group maintenance policies intersect correctly.
- [ ] Cross-midnight maintenance window opens/closes correctly.
- [ ] Maintenance-aware rollout waits outside the window.
- [ ] Next wave begins after the maintenance gate opens.
- [ ] Exact-time typed reboot is dispatched.
- [ ] Next-maintenance-window reboot is dispatched.
- [ ] Reboot success requires a post-dispatch boot-ID change.
- [ ] Natural reboot before dispatch does not falsely satisfy the scheduled reboot.
- [ ] Queued reboot cancellation is guaranteed.
- [ ] Delivered reboot cancellation is reported honestly as potentially continuing.

## H. Network interruption

- [ ] Student offline before delivery: command remains recoverable.
- [ ] Student loses network after delivery but before acceptance: command redelivers safely.
- [ ] Student loses network during update: updater/netqueue reaches a safe retry or rollback state.
- [ ] Controller loses Internet but local services remain coherent.
- [ ] Controller/Fleet API interruption does not corrupt deployment or command state.
- [ ] Reconnection restores telemetry and current/desired reconciliation automatically.

## I. Power-loss / reboot lifecycle

Perform only on sacrificial test Pis with recoverable media:
- [ ] Student power loss before accepting an update.
- [ ] Student power loss after accepting but before update execution.
- [ ] Student power loss during update staging.
- [ ] Controller power loss with queued rollout.
- [ ] Controller power loss during soak.
- [ ] Controller restart while scheduled reboot is pending.
- [ ] SQLite passes integrity check after controller recovery.
- [ ] No command or deployment is silently lost or duplicated.

## J. Release promotion

Required before `0.6.0`:
- [ ] All three GitHub validation workflows green on the exact RC head.
- [ ] No known critical/high-severity release blockers.
- [ ] Fresh controller install passes.
- [ ] Fresh student install passes.
- [ ] Exact-commit update and rollback pass.
- [ ] Canary failure cannot advance.
- [ ] Structured health failure cannot advance.
- [ ] Restart/network interruption idempotency tests pass.
- [ ] Scheduled reboot boot-ID verification passes.
- [ ] Final production image built from the exact release commit passes one zero-to-enrolled smoke test.

After all required gates pass, change `VERSION` to `0.6.0`, run final CI, merge the release PR, tag the exact release commit, then pin the imager to that immutable commit.
